# Project conventions (ov-system)

**Next 16 specifics.** `middleware` is renamed to `proxy.ts` (root). Request APIs are async - `await cookies()` / `await params`. Supabase server client is created **per request** in `src/lib/supabase/server.ts` (never a module-global - that would leak sessions across users).

**Server Actions (`src/lib/actions/*`) must, in order:**
1. Check the role with `can.*` from `src/lib/permissions.ts` (pure RBAC).
2. Validate **all** client input through a Zod schema in `src/lib/actions/schemas.ts` via `parse(schema, input)`. Never trust the raw payload; schemas trim, length-cap, whitelist enums, and strip unknown keys (mass-assignment protection). Add a schema when you add an action; reuse `idSchema` for row identifiers.
3. Mutate through `src/lib/data/repo.ts` **inside a `try/catch`** that returns `errMsg(e)`, then `revalidateEntities(...)`.

Actions return `{ ok: true } | { ok: false; error: string }` (Indonesian error copy). RLS in `supabase/migrations/000x_rls.sql` mirrors these checks as a second layer.

**Never swallow a write error.** Every write in `repo.ts` goes through `must()`, which throws when Supabase returns an error - a write error means the row did *not* change, almost always an RLS denial. Thirty-seven functions used to ignore it, and the symptom was always the same: the optimistic UI keeps the new value, the toast says saved, the data is gone on reload. That masked a total write outage for three roles for weeks. A new repo write wraps its query in `must()`; a new action wraps the call in `try/catch`.

**Access levels.** `MODULE_ACCESS_LEVEL` in `src/lib/constants.ts` is the single source of truth: per module × role, one of `full` (create/edit/delete) → `limited` (create/edit/fill in results, **no delete**) → `view` → `none`. `permissions.ts` derives every `can.*` from it via `atLeast(user, moduleKey, level)` - never hardcode a role list in a `can.*` helper, and add the module row to the matrix instead. Deleting is always `"full"`, so an action that deletes must check `can.deleteX`, not `can.manageX`, and the component needs a separate `canDelete` prop. `MODULE_ACCESS` (nav gating) and the Settings matrix are both generated from the same table.

**An account has no division and no edition scope.** `AppUser` carries neither, deliberately: an account represents a *level of access*, not a person or a team. A role is global - a coordinator is a coordinator for every Ormawa Visit in the database - and one account may be shared by several people. `profiles.division` / `profiles.event_id` still exist in the DB but nothing reads them; leave them alone.

This has bitten the project twice. First in the app (`can.*` filtered by `profiles.division` ⇒ "staff can edit only some tasks"), then in RLS (`owns_scope(event_id, division)` in 0020/0026 ⇒ **every** coordinator/staff/intern write silently failed, because the columns it compares are always null here). Migration **0028** removed it from the database; role is now the only axis on both sides. Don't reintroduce a division or edition filter in `can.*` *or* in a policy.

**There is a hidden Developer layer, and it is an EMAIL, not a role.** `src/lib/developers.ts` reads `DEVELOPER_EMAILS` (gitignored, because this repo is public and the address IS the key) and grants exactly one thing: the `/developer` route. It is deliberately not a sixth `Role` - adding one would print "Developer" in the Settings access matrix, the role-request list, `permissions.ts`, the nav and the Panduan, which is the opposite of hidden. **The route is absent from `NAV`, `GUIDE`, `MODULE_ACCESS_LEVEL` and `APP_ROUTES` on purpose, and `developers.test.ts` fails if any of those gains it.** The guard is `requireDeveloper()` in `guard.ts`, which calls `notFound()` rather than `redirect()`: a redirect confirms the path exists. Two lists exist and both are needed - the env var opens the door, the `developers` TABLE is what RLS checks before returning any data, and the page says so out loud when only one is set up.

**The audit trail is a database TRIGGER, not app instrumentation.** `audit_row()` (0039) fires on every app table, so a write made straight through PostgREST with the public anon key is recorded exactly like one made through a Server Action. Instrumenting ~60 actions instead would have logged only the polite callers, and every action added later would have silently opted out. `activity_log` has a read policy for developers and **no write policy at all** - the trigger is SECURITY DEFINER, so it writes anyway, and nobody can edit or delete the record of their own edits. An UPDATE stores only the changed columns (`updated_at`/`created_at` are stripped BEFORE the comparison, or every no-op save would log a row that says nothing); INSERT and DELETE store the whole row, because there the deleted content is otherwise gone. Bulk scripts set `app.audit = 'off'` (see `reset-data.sql`) so a reset does not bury the real history under thousands of its own deletions.

**An upsert needs a SELECT policy, not just INSERT and UPDATE ones.** `.upsert()` compiles to `INSERT … ON CONFLICT DO UPDATE`, and Postgres requires the target row to be visible under a SELECT policy for that statement shape - even on the first write, when nothing conflicts yet. `presence` shipped with `select using (is_developer())`, so every heartbeat from a normal account was rejected with "new row violates row-level security policy" and the online list only ever contained the developer, who could see their own row. Fixed in 0040 by letting an account read its OWN presence row. When a table is upserted by ordinary users, its read policy has to cover the writer.

**A `bigserial` needs a grant on its SEQUENCE, not just the table.** `error_log` is written by ordinary accounts, and `grant insert (cols) on error_log` alone made every single report fail with `permission denied for sequence error_log_id_seq`. `npm run db:test` caught it; nothing in `tsc`, `eslint` or Vitest could have. Any new table that ordinary users insert into needs `grant usage, select on sequence <table>_id_seq`.

**Archive lock.** `events.locked` makes an edition read-only for every role but admin. `writable_event()` (0028) is the real control; `canWriteEvent(user, event)` in `permissions.ts` is the UX half, and `archivedGuard()` in `actions/lock.ts` turns it into a readable error. Pages hand editable trees an `attenuate(user, event)` identity so a locked edition degrades to read-only without threading a flag through every component. A new write path that touches edition-scoped data needs the guard *and* a policy clause. Opening a module read-only is also not permission to run its destructive actions: when a module moves from `none` to `view` for a role, re-check every write path on that page (e.g. `resetDemoDataAction` needed its own admin check once Pengaturan became readable).

**A link that can be published to Super Link always follows the same contract.** Three places do it now: task results (`task_links`, 0025), prospect links (`prospect_links`, 0038), and nothing else should invent a fourth shape. The child row keeps `in_super_link` plus `link_id`, and `link_id` is what makes re-saving UPDATE the Super Link entry instead of adding a duplicate; unticking the box deletes the entry, deleting the child deletes it, and a partial unique index enforces one owner per entry. `task_refs` (0037) is the deliberate opposite - it POINTS at Super Link, many tasks may point at the same row, so it has no unique index and never writes to `links`. The editor UI is shared too (`components/ui/link-list-editor.tsx`); only the copy differs. `prospects.link` / `link_label` / `link_in_super_link` / `link_id` are legacy columns kept for older rows: 0038 copied them into `prospect_links` and released their ownership, and the Zod schema no longer accepts them from a client.

**Divisions ↔ members.** A member belongs to **many** divisions: `members.divisions` (text[]) is the truth, `members.division` is only the derived primary (`divisions[0]`) kept for older readers. Never compare `m.division === key` - use `memberInDivision` / `memberDivisions` / `primaryDivision` from `src/lib/members.ts`, and write both columns via `divisionFields()` (the actions do this through `withPrimaryDivision`). A division card's team structure is **derived** from that roster; the only thing stored on `teams` is `coordinator` (always a fungsionaris of the same division, and optional - a division may have none). `teams.fungsionaris` / `teams.intern` are legacy: never written any more, still rendered as a fallback while a division has no members assigned, so don't blank them.

**Table filters are checkboxes, and an empty selection means "no filter".** Every filter on every table goes through `components/ui/filter-multi-select.tsx` and stores a `Set<string>`; callers test `picked.size === 0 || picked.has(x)`. Single-select made "show me the accepted AND the rejected prospects" impossible, which is the shape those questions actually have. The division focus is the same control but persisted in a cookie as a comma-joined list (`parseDivisionFocus` / `serialiseDivisionFocus` in `lib/task-filters.ts`), and an empty selection round-trips as the literal `"all"`, never as an empty string - see `getActiveDivision` for the bug that caused. A new filter reuses that component rather than a `<Select>`.

**A clipped note needs a way to unclip it.** `components/ui/expandable-text.tsx` is the only truncation in a table cell: it clamps, and when the text really is cut off it offers Selengkapnya / Tutup. The old pattern (a `truncate` class plus a `title` tooltip) meant the only reliable way to finish reading a catatan was to open the row's EDIT dialog, which a read-only role cannot do at all. It decides whether to show the toggle by MEASURING in a ref callback, not from a character count: the same text clamps in a narrow column and fits in a wide one, and a button that reveals nothing is worse than none. The ref is attached only while collapsed, because an expanded element always reports that it fits.

**Client/server shared cookies.** A constant exported from a `"use client"` module reaches a Server Component as a client *reference*, not its value - reading `store.get(THAT_CONST)` silently returns undefined. Put any cookie name both sides need in a plain module with no directive (e.g. `src/lib/ui-prefs.ts`, `src/lib/demo.ts`).

**Error handling.** `src/app/(app)/error.tsx` is the segment boundary (client, uses `useT()`); `src/app/global-error.tsx` is the self-contained root fallback (no providers/tokens available there). Add EN copy for any new user-facing string in `src/lib/i18n/dict.ts`.

**Backups are manual only.** Scheduled/cron backups were removed in v1.20.0 along with the route, `vercel.json`, and the service-role client - so **no code path in this app bypasses RLS**, and no `SUPABASE_SERVICE_ROLE_KEY` is needed. Keep it that way: an unattended job would need one, and a service-role client behind anything user-reachable erases every guarantee the policies make. `createBackup` refuses to store an empty snapshot, since "zero rows" is what an RLS-filtered read looks like. `kind: "auto"` survives in the type and the DB CHECK only so pre-1.20 rows still render.

**A restore is ONE transaction, and it lives in the database.** `restoreSnapshot` calls the `restore_snapshot(jsonb)` RPC (migration 0043); it does not send DELETEs and INSERTs itself. It used to: fifteen deletes then fifteen inserts over PostgREST, each its own transaction, so a failure on the ninth statement left the database **half restored** with no way back. The plpgsql body is atomic, so any failure rolls everything back. The function is `security invoker` on purpose - RLS still applies, nothing bypasses the policies, and an admin reaches archived editions only because `writable_event()` already returns true for admin. It refuses a non-admin caller with `42501`, turns off row-level audit for its own thousands of writes (the `pre_restore` row in `backups` is the trail), and inserts only the columns the file actually names so a column added after the snapshot keeps its DEFAULT instead of being forced to NULL.

The table order exists **twice** - `DELETE_ORDER` in `src/lib/backup.ts` and `del_order` inside the function, in `setup.sql` and in `0043`. `backup.test.ts` asserts all three match; if they drift, a restore inserts a child before its parent. Add a table to one, add it to all.

**Testing.** Vitest, split into TWO projects by file extension (`vitest.config.ts`). `*.test.ts` runs as project **logic** on the `node` environment: pure logic (permissions, schemas, formatters, scheduling/budget math), which is the bulk of the suite and stays fast. `*.test.tsx` runs as project **components** on `jsdom`, with `src/test/setup-dom.ts` (RTL cleanup plus the ResizeObserver / matchMedia / pointer-capture polyfills Radix needs). Run one project with `npx vitest run --project components`.

The split exists because `include` used to be `*.test.ts` only, so a `.test.tsx` file was **silently not run** - no error, no skip notice. That is how ~130 components ended up with zero coverage while the suite reported 456 green tests, and how two rundown bugs shipped: a nested component definition that remounted every input on each save, and a whole-object `division_jobs` write that reverted the cell edited just before it. `rundown-view.test.tsx` pins both, and both of its regression cases fail against the pre-v1.38.1 code - keep it that way. A component test that cannot fail is worse than none.

Run `npm test` + `npx tsc --noEmit` before finishing a change.

**Seed.** `npm run db:seed` regenerates `supabase/seed.sql` from `src/lib/seed/seed.json`; `npm run db:demo` regenerates the demo project's seed + open-access scripts.

**`supabase/setup.sql` is what you hand the user** - one idempotent, non-destructive file that builds the whole schema (tables, functions, triggers, RLS, column grants) in a single paste, replacing the 28-file `migrations/` run. `migrations/` is kept as history only; several load-bearing decisions and two expensive bugs are recorded nowhere else. A schema change means: write the numbered migration **and** fold it into `setup.sql` in the same commit, then `npm run db:test`. See `supabase/README.md`.

**`npm run db:test`** runs `setup.sql` on a real Postgres (PGlite - WASM, no Docker) and asserts 47 behaviours from the attacker's seat: who may write what, the archive lock, and the self-promotion hole. It exists because **RLS is the only real authorization boundary** (the anon key is public, the session token is in the user's browser, so PostgREST can be called directly) and a policy mistake is invisible to `tsc`, `eslint` and Vitest - that is exactly how a total write outage for three roles shipped and survived for weeks. Run it with `db:lint` whenever you touch SQL.

**`seed.sql` is NOT re-runnable.** It contains 529 `INSERT`s with no `on conflict` clause, so a second run duplicates tasks, members, links, prospects, rundown, job_harih, faqs and teams (`events` and `divisions` are the only guarded ones). This is where the user's recurring duplicate rows came from. To rebuild: backup → `reset-data.sql` → `setup.sql` → `seed.sql` **once** → the import migrations. `reset-data.sql` deliberately leaves `profiles`, `auth.users` and `backups` alone so nobody has to re-register. `npm run db:test` proves the whole loop, including that a double seed really does duplicate.

**Violet (chatbot) never sees a secret in the browser.** GEMINI_API_KEY and GROQ_API_KEY have NO NEXT_PUBLIC_ prefix and lib/violet/{gemini,groq,llm}.ts are `server-only`, so importing one from a client component is a build error rather than a silent leak. That matters here because the repository is public. Retrieval (lib/violet/corpus.ts) reads through the CALLER's repo functions, so RLS decides what Violet can ground on: a Tamu asking about the roster gets nothing to answer from. Retrieval is lexical, not embeddings, and lib/violet/retrieve.ts explains why; an empty result is load-bearing, because that is how the action answers "I do not know" instead of letting the model free-associate. Pin a model with GEMINI_MODEL / GROQ_MODEL only if you must: the defaults are rolling aliases after a pinned version turned out to be already retired.

**Violet has a third corpus: how the system is BUILT.** `lib/violet/system.ts` describes what each entity stores and the rules that are invisible on screen (why a task turns Overtime by itself, who owns a published Super Link entry, what the archive lock actually blocks). The Panduan says which button to press and `live.ts` holds the rows; neither answers "what is a task". That gap is what "Violet only knows about Work Breakdown" was: ask about behaviour and retrieval returned a guide step about clicking Tambah. **When you add a field or change a rule, update the matching passage there in the same change** - same habit as the Panduan, and `system.test.ts` pins one question per passage so a rewrite that makes a passage unfindable fails. Keep it to behaviour and field names: no credentials, no environment variables, no raw DDL.

**Violet's live corpus is one passage per ROW, not per module.** `lib/violet/live.ts` emits a passage for every task, member, division, prospect, rundown session, job, budget item, link and edition, alongside the per-module summaries. The old shape (one paragraph holding every task title) could answer "how many tasks are overdue" and nothing else, and whether a specific fact was reachable depended on how the question was phrased - that was the whole of "Violet sometimes knows and sometimes doesn't". Three things keep it consistent, and all three have tests: `buildCorpus` sorts by id (several getters have no ORDER BY, and `retrieve` breaks score ties by position), `retrieve` breaks ties on id rather than array order, and both providers run at `temperature: 0`. A row passage carries `parent` pointing at its summary, and retrieval pulls that summary in - without it, three matching division rows produced a confident answer listing three divisions out of eleven. Row text deliberately spells out synonyms ("deadline, tenggat, batas waktu"): retrieval is lexical, so a passage is only findable through words it literally contains.

**The prompt budget is set by the free tier, not by the model.** Measured on the real thing: a 14,000-character context cost ~6,200 tokens per question, and Groq's free tier allows 12,000 tokens per MINUTE, so the backup provider ran dry after two questions and the point of having a backup was lost. `CONTEXT_BUDGET` (6,500 chars), `DEFAULT_LIMIT` (14 passages), the 6-turn/1,200-char history cap in `violetAskSchema`, `max_tokens: 900`, and the one-line `routeCatalogue()` are all that same constraint. Anything you add to the system prompt is paid for on every question by every user; check `preview_logs` for Groq's own "Requested N tokens" accounting after changing it.

**Violet runs on free tiers, so a spent quota is a normal Tuesday.** `lib/violet/llm.ts` is a provider CHAIN (Gemini, then Groq) behind one `generate()`; a provider with no key is skipped silently and the Violet button hangs off `violetConfigured()` being true for *any* of them. Providers return a CODE, never the vendor's English prose: `lib/violet/errors.ts` owns the classification (a 429 is "out for the day" or "going too fast" depending only on the wording, and the two need opposite advice), the Indonesian copy, whether a retry button is worth showing, and whether the next provider should be tried at all. A safety refusal must NOT fail over: the second model refuses the same question, just more slowly. When adding a provider, add it to `CHAIN` and disclose it in `lib/legal.ts` (`legal.test.ts` fails on an undisclosed processor).

**Violet must never hand out a link to a page that does not exist.** It shipped one to `/violet`, a guide section that is not a menu, and a dead shortcut reads as an authoritative answer that ends in a 404. `lib/violet/links.ts` is the single registry of real paths and their in-page anchors: `resolveHref` gates every href, both the corpus's own (`buildCorpus` sweeps them at the end) and any markdown link the model writes (`components/violet/rich-text.tsx` renders an unknown path as plain text). Listing the paths in the prompt is the polite half of the fix; dropping what is not on the list is the half that holds. When you add a route or an anchor `id`, add it to `APP_ROUTES` too, and keep `links.test.ts` green: it cross-checks the table against `NAV` and `GUIDE`.

**Answers are markdown, rendered by a whitelist.** The model emits markdown whether or not you ask, and the bubble used to print it literally. `lib/violet/markdown.ts` is a pure parser (bold, italic, inline/fenced code, headings, quotes, bullet and numbered lists, links) and `rich-text.tsx` builds real React elements from it. There is no `dangerouslySetInnerHTML` and no HTML passthrough anywhere in that path, so there is nothing for a sanitiser to do; keep it that way.

**In-page anchors need `AnchorScroller`, not the browser.** Client-side navigation renders the destination after the URL changes, collapsed `<details>` have no layout to scroll to, and the sticky topbar would cover the heading. `lib/scroll-to-anchor.ts` handles all three (retry window, opens ancestor `<details>`, offset, plus a flash so arriving mid-page does not look like nothing happened) and `components/layout/anchor-scroller.tsx` mounts it once in the app shell. A tabbed page needs its own hash handling as well, since only one tab is mounted: see `guide-tabs.tsx`.

**No em dashes, anywhere.** Not in UI copy, comments, SQL, changelog, or docs. Use a comma, a colon, brackets, a full stop, or a spaced hyphen. 774 of them had piled up across 147 files before the sweep, so `src/lib/no-em-dash.test.ts` scans every `.ts/.tsx/.js/.mjs/.sql/.md/.css` file and fails with the offending `file:line`. It also asserts it can still detect one, so the guard cannot quietly go vacuous. The changelog has its own house style at the top of `src/lib/changelog.ts`: one line per change, one sentence, plus a `kind` (`new` / `fix` / `security` / `ui` / `data`).

**Every user-facing string needs an EN entry in the same change.** `translate()` falls back to the Indonesian source when a key is missing, which is graceful but silent - 60 strings accumulated that way before anyone noticed. `src/lib/i18n/coverage.test.ts` now scans the source for `t("…")` / `tr("…")` literals and fails when one has no entry in `dict.en.ts`. An entry whose value equals its key is fine (loanwords like "Kanban", "Deadline", "Qty"); a blank value is not.

**Never use a temporary table in SQL you hand the user.** A temp table lives in one session, and the Supabase SQL Editor talks to the database through a connection pooler - the next statement can land on a different backend, and the script dies with a bare `ERROR: 42P01: relation "…" does not exist` pointing at the wrong line. This shipped once (0030) and failed on the user's first run. Anything needing intermediate rows must fit in ONE statement: a `with … as (values …)` CTE (repeat it per statement if two statements need it), or a `DO $$ … $$` block that does all its work internally. `npm run db:lint` now rejects `create temporary table` outright, and `npm run db:test` replays every pending migration **one statement at a time** - the same way the editor does - plus a second time for idempotency.

**SQL you hand the user must be linted.** `npm run db:lint` runs `scripts/sql-lint.mjs` over every file in `supabase/` - both generators also call `assertSqlSane()` before writing, so a broken file never reaches disk. It exists because two classes of bug shipped straight to the SQL editor: an interpolated value closing a `'…'` literal early (quotes still *balance*, so nothing else catches it), and a `--` comment containing `$$` inside a `do $$ … $$` block, which ends the block early because **dollar-quoting is lexical and comments do not protect it**. Keep prose out of dollar-quoted bodies, and dollar-quote (`$sql$…$sql$`, distinct tag) any `execute` string that contains quotes.

**The demo project's schema is a SUBSET of production's.** It is at 0001–0018 + 0027 and must never get `0019_real_roster.sql` (that wipes the roster and inserts real people). So a migration cannot assume a column added by 0019+ exists there - 0027 adds `teams.coordinator` itself for this reason. `supabase/demo/demo-seed.sql` is re-runnable (it deletes the `demo-ov` edition's rows first), has a **"Part 0" schema catch-up** that idempotently adds columns from later migrations the demo never runs (perf-measurement from 0029, `rundown.merges` from 0031), and guards `task_links` with `to_regclass`, since 0025 may be absent. When the app starts writing a new column, add it to that catch-up or the demo breaks with "Could not find the '…' column".

**`setup.sql` and the migration path can drift - a policy fix must land in BOTH.** `setup.sql` is a from-scratch build; production runs migrations one by one. When you tighten a policy, replacing it in `setup.sql` is not enough: the production DB still has whatever the migrations left it. Worse, permissive RLS policies are OR-ed, so a *new* scoped policy sitting next to a *stale* loose one leaves the loose one winning - that is exactly how archived `task_links` stayed writable (0025's `task_links_write` was never dropped when 0028 added the scoped versions; fixed by 0034). A policy change needs a migration that DROPs the old policy by name, not just a fresh `create`. `npm run db:test` reproduces the stale-migration state and proves the fix, separately from the setup.sql end-state.

**Roster is PII.** `members` and `teams` carry names and NRP (student IDs), so their read policy is `has_role()`, not the blanket `auth.uid() is not null` used for other operational tables - Tamu (anonymous *and* registered-viewer) cannot read them. It is a row-level hide, not column masking (PostgREST can't mask per-session without a view), so guests see an empty roster; the `/members` page shows a notice so that reads as intentional, not broken.

**Legal pages.** `src/lib/legal.ts` holds the Privacy Policy and Terms of Service as bilingual data (same `{ id, en }` pattern as `guide.ts`), rendered by `components/legal/legal-document.tsx` at `/privacy` and `/terms`. Both routes live OUTSIDE the `(app)` group and are in `proxy.ts`'s public paths - they must be readable before you have an account. **They describe what the app actually does, so when you add a data field, a cookie, or a third-party service, update the matching section in the same change**; `legal.test.ts` fails if a cookie or processor goes undisclosed, or if a string is missing its English translation.

**Panduan (user guide).** `src/lib/guide.ts` holds the per-feature usage guide as data, with Indonesian **and** English in the same entry (`{ id, en }`) - it follows the language toggle without going through `dict.ts`. Rendered by `components/panduan/guide-sections.tsx` under `/panduan`, below the flowchart. **Whenever you add or change a user-facing feature, update that feature's section here in the same change** (purpose / steps / tips / access), in both languages. Add a new `GuideSection` when you add a menu, and keep `key` equal to the nav/module key.

**Versioning (v1.x.y).** The version scheme is `v1.x.y`: the leading `1` is **LOCKED - never change it**. Bump `x` (minor) for a big/feature update and reset `y` to 0; bump `y` (patch) for a small fix. On every shipped change you MUST: (1) update `APP_VERSION` in `src/lib/version.ts`, (2) prepend a matching entry to `CHANGELOG` in `src/lib/changelog.ts` (Indonesian copy, newest first), and (3) keep the footer in sync - it reads `APP_VERSION` from `src/components/layout/app-shell.tsx`, so no manual edit needed there. The Settings page renders the changelog automatically.

**Accounts & role requests.** Anyone can self-register (`/signup`, email+password or Google; OAuth returns through `/auth/callback`). The `handle_new_user` trigger gives every new account role `viewer` → the app's read-only "Tamu". They then file a role request from the user menu or the amber banner; an admin approves it in `/roles`. Approval must go through the `decide_role_request` SECURITY DEFINER RPC - `profiles.role` is deliberately not writable by `authenticated` (that's the fix for the self-promotion hole in migration 0020). Add `/signup` and `/auth/*` to `proxy.ts`'s public paths if you touch that list.

`requestableRolesFor(user)` in `permissions.ts` is the authority on what may be requested: never `admin`, never the role the account already holds, nothing for admins (so they can't be demoted this way) and nothing for anonymous Tamu sessions. A role is global - requests carry **no** event scope (`role_requests.event_id` is retained but deprecated, see 0024). A pending request is editable by its owner and immutable once decided.

**Demo mode = a SEPARATE Supabase project.** Demo and real data live in different databases and can never cross. `src/lib/demo.ts` (dependency-free, client+server) holds `DEMO_COOKIE`, `demoConfigured()`, and `supabaseCreds(demo)`. The single choke point is `supabase/server.ts` (+ `supabase/client.ts` for the browser): when the `ov_demo` cookie is set AND `NEXT_PUBLIC_SUPABASE_DEMO_URL`/`_ANON_KEY` are configured, every Supabase client points at the demo project. `proxy.ts` skips auth/redirect in demo mode; `getCurrentUser` (auth.ts) returns a `DEMO_USERS` identity (default admin, role-switchable) with no production auth. Enter/exit via `enterDemoMode`/`exitDemoMode` (`actions/session.ts`); the login page shows a "Coba Mode Demo" button when configured, and `DemoBanner` + the RoleSwitcher render while in demo. The demo project's mockup seed + open-RLS script are generated by `npm run db:demo` (`scripts/gen-demo-seed.mjs` → `supabase/demo/`). The demo project uses the anon key with no login, so `demo-open-access.sql` disables RLS there - never run it on production.

**Copying data between editions (`cloneEventData`).** The event form can seed a new edition, or overwrite an existing one, from another. `CloneSources` maps each menu (`CLONE_MODULES`) to the source edition id; `CloneFilters` narrows it (task/member copy to specific division keys, budget to specific plan ids); `opts.replace` chooses wipe-then-copy vs append. **The repo and the local JSON mirror must stay in lock-step** - both implement the same clear/copy branches, and a menu added to `CLONE_MODULES` needs a branch in each plus a label in `clone-picker.tsx`. Super Link entries that were PUBLISHED from a task/prospect (`source !== "manual"`) are skipped by the links copy: they are owned by their source row and a free copy would be an orphan. On EDIT the copy is destructive, so the dialog requires an explicit mode choice AND a confirmation checkbox naming both editions before the submit button enables. `getCloneOptionsAction` (read-only, so exempt in `guards.test.ts`) fetches a source's divisions/plans on demand rather than eagerly for every edition.

**Compare subjects are explicit (migration 0041).** A `compare_subjects` row is one association being weighed up, created from the "Buat perbandingan" button, NOT derived from the accepted-prospect list. `compare_entries` hang off it via `subject_id` (cascade). Two partial unique indexes enforce "can't compare the same association twice per edition" - one on `(event_id, prospect_id)`, one on `(event_id, lower(org_name))` for imported subjects that have no prospect. When you catch a Postgres `duplicate key` here, translate it to human copy rather than surfacing the constraint name. The one-off `0042_compare_hmd_eksternal_data.sql` was generated by `scripts/gen-compare-seed.mjs` from two CSVs (uncommitted, the user's working docs) - regenerate, never hand-edit, and it stays out of `setup.sql` because it targets one specific edition (`ov2-2026`).
